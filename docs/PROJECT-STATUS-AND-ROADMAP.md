## 1. Executive summary

Zenith is being built as a local-first Windows AI development workbench. The intended product combines:

- one visible master orchestrator;
- editable Soul, Role, Agent, Skill, Command, Plugin, and Profile definitions;
- explicit `/` commands and `@file` context selection;
- OpenAI, Anthropic, OpenRouter, NVIDIA NIM, and local-compatible model providers;
- local project browsing, reviewable diffs, recoverable edits, tests, terminal, and hardened Git inspection;
- trusted plugins and MCP-compatible tools;
- a later optional push-to-talk/floating voice companion.

Gates G0-G3 are complete. Today, the repository contains a tested and packaged security foundation, one bounded offline coding loop, and a complete manageable-but-inert definition studio: a hardened Electron shell, typed IPC, approval capabilities, separate trust state machines, durable SQLite state, encrypted credential storage, bounded audit/diagnostics, one controlled file replacement, one fixed verifier, one selected-file read-only Git inspection, and visible Soul/Role/Agent/Skill/Command/Profile/Plugin records with approved lifecycle and transfer seams.

It does **not** yet contain a general or network-backed AI coding assistant. It can open and preview exactly one explicitly selected bounded UTF-8 file, ask one fixed zero-egress fake provider to create an exact-diff proposal, obtain a separate exact approval, apply that one file once, inspect redacted durable recovery state, explicitly approve one immutable local verifier whose bounded textual output and exit state appear in the Tests panel, and explicitly inspect bounded read-only Git state/diff for that selected file. It cannot enumerate a project, call an external model provider, execute an agent or skill, run a generic terminal command, mutate Git, or start a plugin. Those capabilities are deliberately added in later gates after their authority and failure modes are designed and tested.

## 5. Engineering rationale used so far

This section records the reviewable engineering rationale and decision criteria used by the project. It is not a transcript of private internal reasoning.

### 5.1 Local-first before network-first

The application is being made useful offline before real provider integration. This gives us deterministic fixtures, no credential requirement, no accidental egress, and a stable way to prove edits and approvals before adding model variability.

### 5.2 Authority grows one gate at a time

Each milestone adds one bounded class of authority. G0 could launch and package. G1 could persist policy/security state. G2 added one controlled and reproducible file-edit loop. Later gates add definitions, real network providers, full workspace operations, orchestration, terminal processes, and executable plugins.

This order prevents a broad AI feature from being built on an untested privileged foundation.

### 5.3 Deny by default

Unknown IPC operations, malformed records, wrong senders, stale versions, replayed approvals, changed proposals, expired capabilities, untrusted configuration, unexpected paths, and unavailable encryption all fail closed.

### 5.4 Separate trust from approval

Trust answers whether a source or workspace may participate at all. Approval answers whether one exact consequential action may run once. A trusted workspace does not grant unlimited actions, and a Markdown file cannot grant trust or mint approval capabilities.

### 5.5 Make consequential actions inspectable

Actions are represented as typed proposals with exact targets, arguments, hashes, policy, identity, risk, and expiry. The goal is not merely to show a generic confirmation dialog; it is to bind consent to what will actually execute.

### 5.6 Keep privileged code out of the renderer

The renderer is designed as replaceable, untrusted UI. It receives narrow, validated results and never receives a credential reveal API, raw IPC subscription, filesystem handle, shell function, or unrestricted Electron object.

### 5.7 Test denial and recovery, not only success

Every powerful path must have tests for malformed input, wrong ownership, replay, drift, cancellation, timeout, crash/restart, conflict, recovery, and redaction. A happy-path demonstration alone is not considered sufficient evidence.

### 5.8 Use evidence instead of optimistic claims

Each completed phase records commands, exit codes, versions, hashes, limitations, RED/GREEN behavior, and a real Electron screenshot. Packaging is inspected from the actual ASAR/executable rather than inferred from source configuration.

### 5.9 Be honest about OS boundaries

Electron sandboxing protects the renderer boundary but does not turn arbitrary same-user executable code into a secure sandbox. Terminal commands, executable plugins, and MCP stdio servers will be described as having the current Windows user's authority.

Likewise, encrypted local credential storage protects data at rest but cannot promise protection from every process already running as the same logged-in user.

### 5.10 Prefer recoverability over false atomicity

Future multi-file edits will use journals, base hashes, temporary replacements, and explicit partial/recovery states. The project will not claim cross-file filesystem atomicity where Windows cannot guarantee it.

### 5.11 Preserve user control and visible dissent

The master may recommend agents, skills, or actions, but selection and consequential execution remain visible. When independent reviewers or agents disagree, the eventual orchestrator must retain the disagreement rather than silently presenting a false consensus.

### 5.12 Optimize only after measurement

Performance work will use named fixtures and recorded hardware/profile measurements. Complexity will not be added for speculative optimization.

## 6. Decision process going forward

Every new capability should follow this sequence:

1. **Define the user outcome.** State what becomes possible and what remains deliberately impossible.
2. **Classify authority and data.** Identify filesystem, process, network, credential, trust, and persistence implications.
3. **Draw the boundary.** Decide which process owns the capability and define the smallest typed interface.
4. **Define the proposal.** Consequential actions need exact targets, arguments, identity, hashes, policy, risk, and expiry.
5. **Design denial and recovery first.** Specify malformed input, stale state, cancellation, crash, conflict, partial completion, and rollback behavior.
6. **Write a focused failing test.** Capture RED evidence for the missing behavior or vulnerable state.
7. **Implement the minimum complete behavior.** Avoid adding adjacent authority that belongs to a later gate.
8. **Prove exact runtime behavior.** Use real Electron/Windows fixtures where browser or Node-only tests are insufficient.
9. **Inspect the package boundary.** Confirm that the production artifact retains security controls and excludes source, secrets, and development paths.
10. **Record evidence and limitations.** Update task state, evidence, durable documentation, and the phase screenshot.
11. **Prepare the phase handoff.** Report the exact verified phase files and checks. The user currently owns staging, commits, and GitHub pushes unless a later exact request delegates them again.
12. **Run the milestone gate.** Reproduce from a clean source tree and ensure earlier gates remain green.

Questions used during design and review will include:

- What new authority does this feature introduce?
- Can untrusted repository/model/plugin content influence it?
- What exact identity is approved, and can that identity drift?
- What happens if the app crashes between intent and effect?
- What remains running or remote after cancellation?
- Where could a credential, prompt, file, or log leak?
- Can the renderer or another sender bypass the privileged broker?
- Can the behavior be reproduced without hidden machine-global state?
- What evidence would disprove our security or reliability claim?
- Are we describing a real guarantee, a cooperative control, or only a warning?
